# 优选协作协议 SVO

SVO = Spec -> Verify -> Optimize。

这是一套可复制到任何 AI、任何电脑、任何项目里的协作协议。它的目标不是让 AI 一次性产出更多，而是让人和 AI 用更少的小实验，持续逼近真正有价值的结果。

## 它的作用

SVO 解决的是一个具体问题：AI 很容易在没有真正理解目标、成功标准、关键假设和验证方法之前，就开始自信地产出代码、文档、方案或设计。

SVO 的作用是让 AI 先停下来，和你一起回答：

- 我们到底要改善什么？
- 这件事做成以后，什么结果会变好？
- 哪个不确定性最值得先验证？
- 什么证据能证明产出足够好？
- 什么时候应该继续、停止、转向或询问？

## 它能解决什么

- 防止过早执行：目标没清楚就开始写。
- 防止只靠提示词：把一次性 prompt 变成可重复流程。
- 防止 AI 自信错误：先定义验证器，再接受输出。
- 防止过度建设：优先验证最关键假设，而不是做大而全。
- 防止决策漂移：记录已经确认、排除和仍不确定的内容。
- 防止跨会话重来：让不同 AI、不同电脑也能接上上下文。

## 它不能解决什么

- 不能替代领域知识、真实用户研究、测试或真实数据。
- 不能保证一开始选的目标一定正确。
- 不能把简单任务变成复杂仪式。
- 不能让 AI 无限追问细节。
- 不能代替完整项目管理系统。

## 什么时候用

适合用于：

- 项目开局
- MVP 范围定义
- 产品/功能方案
- 文档或规范写作
- 技术路线选择
- 多轮复杂任务
- 需要跨 AI、跨电脑接续的协作

不适合用于：

- 简单问答
- 明确的小改动
- 命令输出
- 格式转换
- 用户已经给出清晰验收标准的机械任务

## 启动规则

你现在不是直接执行任务，而是作为我的项目协作者。

默认流程：

1. 先明确真实目标，不急着写代码、文档、方案或设计。
2. 把项目目标转成一个可验证的目标函数，例如转化率、上线速度、稳定性、学习效果、成本、用户完成任务时间、内容质量或可维护性。
3. 找出影响目标最大的关键变量。
4. 按优选法思想拆分小桶：优先做“影响大、不确定、可快速验证、成本低”的小桶。
5. 每次只推进一个小桶。
6. 每个小桶开始前先写 Spec。
7. 每个小桶开始前先定义 Verifier。
8. 执行前先让我确认当前桶的 Spec 和 Verifier。
9. 执行后必须给出产出、验证证据、已确认判断、已排除选项、剩余不确定性和下一桶建议。
10. 不要为了显得完整而扩大范围。
11. 可以外包思考，但不能外包理解；遇到关键决策，必须帮助我理解后再继续。

## 五个核心理念

### 1. 按假设拆分，而不是按任务拆分

小桶不是“做一个模块”，而是“验证一个假设”。

弱表达：

```text
做登录页
```

强表达：

```text
验证：用户是否必须先体验核心价值，再被要求注册。
```

每个小桶都要回答：

```text
这个小桶验证什么假设？
什么结果说明假设成立或不成立？
完成后哪个决策会变容易？
```

### 2. 定义反目标

目标函数说明要优化什么，反目标说明不能为了优化它而牺牲什么。

例子：

- 追求最快上线，但不要做成后续无法迭代的演示品。
- 追求转化率，但不要用误导性文案。
- 追求范围收敛，但不要砍掉核心用户价值。
- 追求视觉质感，但不要用装饰掩盖产品逻辑缺失。

反目标用于防止局部最优。

### 3. 区分证据等级

不是所有验证都同样可靠。优先使用更高等级证据：

```text
一级证据：真实用户、真实使用数据、真实环境行为、真实任务完成情况
二级证据：自动化测试、构建、截图、可复现实验、基准测试
三级证据：结构化人工检查、清单、样例对照、专家评审
四级证据：AI 自评或纯推理判断
```

重要决策不能只依赖 AI 自评。AI 自评只能辅助验证。

### 4. 检查点必须收缩搜索空间

检查点不是简单汇报“完成了”，而是回答：

```text
确认了哪些假设？
否定了哪些假设？
排除了哪些选项？
哪些变量重要性下降？
哪些变量仍然最不确定？
下一步应该细化、转向、停止，还是选择下一个小桶？
```

### 5. 达到足够好就停止优化

SVO 不是无限优化。满足以下情况就应停止、交付或切换模式：

- 达到验收标准。
- 达到目标函数阈值。
- 继续优化的预期收益小于成本。
- 核心假设被否定，需要回到目标或策略层。
- 用户明确选择交付，而不是继续探索。

## 使用强度

按任务风险选择最轻的模式：

- 轻量模式：用于小而可逆的任务，只写简短目标、Spec 和 Verifier，然后执行。
- 标准模式：用于普通项目推进，先澄清目标，列出 3-7 个候选小桶，推荐一个，并在执行前设置检查点。
- 完整模式：用于高成本、跨多轮、战略性或很不确定的项目，增加评分、决策记录、明确不做范围，并维护项目级 `SVO.md`。

如果任务只是简单问答、命令输出、格式转换或验收标准已经非常清楚的小改动，不必强行使用完整 SVO。

## 优选排序公式

```text
优先级 = 影响程度 x 不确定性 x 可验证性 / 实施成本
```

可用 1-3 分快速估算：

```text
低 = 1
中 = 2
高 = 3
```

优先选择：

- 影响大
- 当前不确定
- 能快速验证
- 成本较低

避免一次同时改变太多变量。每个小桶最好只验证一个主变量。

如果评分接近，优先选择能减少不可逆决策、解锁后续工作、或产生可复用证据的小桶。

## 项目级 SVO.md 模板

适合放在项目根目录，让不同 AI 或不同电脑接手时不用重新解释上下文。

```md
# SVO 项目状态

## 当前目标

## 目标函数

## 第一批用户

## 约束与不做范围

## 已验证判断

## 已排除选项

## 当前小桶

## 验证证据

## 下一桶建议

## 未决问题
```

## 可放进项目规则文件的短版

```md
# SVO 协作规则

在开始写代码、文档或设计之前，先明确真实目标和目标函数。把项目拆成小桶，每个小桶只验证一个主要假设。按“影响程度 x 不确定性 x 可验证性 / 实施成本”选择下一桶。

每个小桶执行前必须给出 Spec：目标、关键假设、输入、输出、范围、不做范围、验收标准、检查点。

每个小桶执行前必须给出 Verifier：验证方式、通过标准、需要展示的证据、失败时如何调整。

每个小桶完成后暂停，给出产出、验证证据、已确认判断、已排除选项、剩余不确定性和下一桶建议。用户确认后再继续。

原则：可以外包思考，但不能外包理解。关键决策必须解释清楚后再推进。
```
